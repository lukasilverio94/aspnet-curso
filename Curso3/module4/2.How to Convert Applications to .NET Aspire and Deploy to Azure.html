Converting ASP.NET Core to .NET Aspire Cloud-Native Application

Introduction

This tutorial demonstrates how to transform a traditional multi-product ASP.NET Core application into a .NET Aspire cloud-native application with built-in observability, automatic service discovery, and seamless Azure deployment. This conversion simplifies both development and deployment while adding powerful monitoring capabilities.

Existing Application Structure

The starting point is a traditional e-commerce application with three separate projects:

  • Shopping.App.API: Backend API project
  • Shopping.App.Web: Frontend web application
  • Shopping.AppData: Data access layer

Currently, each project runs independently with manual configuration for inter-service communication.

Creating the .NET Aspire App Host Project

The first step in the conversion is to create a new .NET Aspire App Host project, which will serve as the orchestration center for the distributed application.

Terminal Command

dotnet new aspire-apphost -n ShoppingApp.AppHost

This command creates the App Host project with a typical C# project structure, including a Program.cs file where the application topology will be defined.

Note: The App Host project serves as the orchestration center for your distributed application. It defines how services connect and communicate with each other.

Adding Projects to the App Host

After creating the App Host project, the next step is to register the existing API and Web projects.

Adding the API Project

In the App Host's Program.cs file, add the API project right after the builder declaration:

var apiService = builder.AddProject<Projects.ShoppingApp_API>("shoppingapp-api");

Adding the Web Project with Service Reference

Next, add the web project with a reference to the API. This establishes the dependency and automatically configures service discovery:

builder.AddProject<Projects.ShoppingApp_Web>("shoppingapp-web")
    .WithReference(apiService);

The WithReference method automatically configures service discovery so the web project can find and communicate with the API.

Creating the Service Defaults Project

The Service Defaults project provides consistent configurations for observability, health checks, and other cross-cutting concerns across all services.

Step 1: Create the Project Folder

Create a new folder named ShoppingApp.ServiceDefaults in your solution directory.

Step 2: Navigate to the Folder

cd ShoppingApp.ServiceDefaults

Step 3: Create the Service Defaults Project

dotnet new aspire-servicedefaults

This project will be referenced by all other service projects to ensure consistent configuration across your application.

Updating Services to Use .NET Aspire

Each service project needs to be updated to use the Service Defaults configuration.

Updating the API Project

Open the Program.cs file in the Shopping.App.API project.

Step 1: Add Using Statement

Add the following using statement at the top of the file:

using ShoppingApp.ServiceDefaults;

Step 2: Add Service Defaults Configuration

Add the following line to configure the service defaults (typically after the builder is created):

builder.AddServiceDefaults();

This single line automatically configures observability, health checks, and other .NET Aspire features for the service.

Important: Remember to save the Program.cs file after making these changes.

Adding Observability Features and Redis Caching

Return to the App Host configuration to add additional infrastructure components and observability features.

Adding Redis Cache

In the App Host's Program.cs, add Redis caching to demonstrate how .NET Aspire handles infrastructure components:

// Add Redis caching
var redis = builder.AddRedis("cache");

Connecting Redis to the Web Application

Connect the Redis cache to the web application by adding a reference:

builder.AddProject<Projects.ShoppingApp_Web>("shoppingapp-web")
    .WithReference(apiService)
    .WithReference(redis);
Key Feature: Notice how .NET Aspire automatically handles Redis container management, networking, and configuration injection. You don't need to manually configure connection strings or container orchestration.

Key .NET Aspire Concepts

App Host Project
The orchestration center that defines the application topology, service dependencies, and infrastructure components. It manages how services discover and communicate with each other.
Service Defaults
A shared project that provides consistent configuration for observability, health checks, resilience patterns, and other cross-cutting concerns across all services.
Service Discovery
Automatic configuration that allows services to find and communicate with each other without hardcoded URLs or manual configuration.
WithReference Method
Establishes dependencies between services and infrastructure components, enabling automatic service discovery and configuration injection.
Infrastructure Components
Built-in support for common dependencies like Redis, SQL Server, and RabbitMQ with automatic container management and configuration.
Built-in Observability
Automatic configuration of logging, metrics, and distributed tracing across all services in the application.

Benefits of .NET Aspire

  • Simplified Development: Automatic service discovery eliminates manual configuration of service URLs and endpoints
  • Built-in Observability: Logging, metrics, and distributed tracing are configured automatically
  • Consistent Configuration: Service Defaults ensure all services follow the same patterns for health checks, resilience, and monitoring
  • Infrastructure Management: Automatic handling of containers, networking, and configuration for dependencies like Redis and databases
  • Seamless Deployment: Easy deployment to Azure with built-in support for cloud-native patterns
  • Developer Experience: Unified orchestration through the App Host simplifies running and testing distributed applications locally

Conclusion

Converting a traditional ASP.NET Core application to .NET Aspire involves three main steps:

  1. Creating an App Host project to orchestrate services
  2. Creating a Service Defaults project for consistent cross-cutting concerns
  3. Updating each service to reference Service Defaults and registering them in the App Host

The result is a cloud-native application with automatic service discovery, built-in observability, simplified infrastructure management, and streamlined deployment capabilities. .NET Aspire handles the complex orchestration and configuration tasks, allowing developers to focus on building features rather than managing infrastructure.
