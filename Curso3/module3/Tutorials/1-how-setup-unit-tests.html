Setting Up Your First Unit Test Project in ASP.NET Core with xUnit

Complete guide to creating a test project structure and running your first unit test

Learning Objectives

By the end of this demonstration, you will be able to:

  • Create a complete unit test project structure using xUnit
  • Organize projects using a .NET solution file
  • Configure project references between test and application projects
  • Understand the essential NuGet packages for unit testing
  • Create and run your first test to verify the setup

Goal: You'll have a complete test project structure that's ready for writing unit tests and verification that everything is working correctly.

Prerequisites

  • .NET SDK installed (version 6.0 or later recommended)
  • Visual Studio Code with C# extension
  • Basic familiarity with command-line interface
  • Understanding of ASP.NET Core project structure

Opening the Integrated Terminal

Accessing the Terminal in Visual Studio Code

Step 1: Navigate to the Terminal menu in the top menu bar
Step 2: Select "New Terminal" from the dropdown menu

Alternative Methods: You can also open a new terminal using:

  • Keyboard shortcut: Ctrl + Shift + ` (Windows/Linux) or Cmd + Shift + ` (Mac)
  • View menu → Terminal

Navigating to Project Destination

Once the terminal is open, navigate to your desired project destination folder using the cd command.

cd path/to/your/projects

Creating a New Solution

Why Use a Solution File?

A solution file (.sln) organizes multiple related projects in one container, making it easier to:

  • Manage dependencies between projects
  • Build all projects together
  • Open the entire project structure in Visual Studio or VS Code
  • Share configuration across multiple projects

Creating the Solution

Create a new solution named "MathApp" using the .NET CLI:

dotnet new sln -n MathApp

Command Breakdown

Parameter Purpose
dotnet new Creates a new project or file from a template
sln Specifies the solution file template
-n MathApp Names the solution "MathApp"

Success: The solution file MathApp.sln was created successfully in the current directory.

Creating the Main Application Project

Creating an ASP.NET Core Web API Project

Create the main application project that will be tested:

dotnet new webapi -n MathApp.API

Command Breakdown

Parameter Purpose
dotnet new Creates a new project from a template
webapi Specifies the ASP.NET Core Web API template
-n MathApp.API Names the project "MathApp.API"

What Gets Created

This command creates a new ASP.NET Core Web API project with:

  • Controllers folder with sample WeatherForecast controller
  • Program.cs file with application configuration
  • appsettings.json for configuration
  • Project file (MathApp.API.csproj) with necessary dependencies

Result: A new ASP.NET Core Web API project is created in the MathApp.API folder, ready to be tested.

Creating the Test Project

Creating an xUnit Test Project

Create a dedicated test project using the xUnit template:

dotnet new xunit -n MathApp.Tests

Command Breakdown

Parameter Purpose
dotnet new Creates a new project from a template
xunit Specifies the xUnit test project template
-n MathApp.Tests Names the test project "MathApp.Tests"

Result: A new test project is created with xUnit already configured and ready to use.

Essential NuGet Packages Included

The xUnit project template automatically includes these essential NuGet packages:

Package Purpose
xunit Core xUnit testing framework with attributes and assertions
Microsoft.NET.Test.Sdk Required for test discovery and execution
xunit.runner.visualstudio Enables Visual Studio Test Explorer integration
coverlet.collector Provides code coverage analysis capabilities

These packages work together to provide test discovery, execution, and code coverage reporting.

Adding Projects to the Solution

Why Add Projects to the Solution?

Adding projects to the solution allows you to manage them together and enables easy building, testing, and deployment of the entire application.

Adding the API Project

Add the main API project to the solution:

dotnet sln add MathApp.API\MathApp.API.csproj

Success: The MathApp.API project has been added to the MathApp solution.

Adding the Test Project

Add the test project to the solution:

dotnet sln add MathApp.Tests\MathApp.Tests.csproj

Success: The MathApp.Tests project has been added to the MathApp solution.

Command Pattern

dotnet sln add [path-to-project]\[project-name].csproj

Verification: You can verify that both projects are in the solution by running:

dotnet sln list

This displays all projects currently in the solution.

Adding Project Reference

Why Add a Project Reference?

The test project needs a reference to the main application project so that:

  • Tests can access the classes and methods in the API project
  • The test project can instantiate and test API components
  • Changes in the API project trigger recompilation in the test project
  • Dependencies are properly managed during build and deployment

Navigating to the Test Project Directory

First, change to the test project directory:

cd MathApp.Tests

Adding the Project Reference

Add a reference from the test project to the API project:

dotnet add reference ..\MathApp.API\MathApp.API.csproj

Command Breakdown

Component Purpose
dotnet add reference Adds a project-to-project reference
.. Navigates up one directory level
MathApp.API\MathApp.API.csproj Path to the API project file

Success: The reference has been added successfully. The test project can now access and test classes from the API project.

Returning to the Root Directory

Navigate back to the root directory:

cd ..

What Happens Behind the Scenes: Adding a project reference updates the test project's .csproj file to include:

<ItemGroup>
  <ProjectReference Include="..\MathApp.API\MathApp.API.csproj" />
</ItemGroup>

Understanding the Sample Test

Examining UnitTest1.cs

The template includes a sample test file to verify the setup:

namespace MathApp.Tests;

public class UnitTest1
{
    [Fact]
    public void Test1()
    {
        Assert.True(true);
    }
}

Breaking Down the Test Structure

Namespace Declaration

namespace MathApp.Tests;

File-scoped namespace declaration (C# 10+) that applies to the entire file.

Test Class

public class UnitTest1

A public class that contains test methods. Test classes should be public so the test runner can discover them.

Test Method

[Fact]
public void Test1()

[Fact] Attribute: Marks a method as a test case that:

  • Takes no parameters
  • Should always produce the same result
  • Will be discovered and executed by the test runner

Test Assertion

Assert.True(true);

A simple assertion that always passes. The Assert class provides various methods for verifying expected outcomes.

Next Steps: Writing Real Tests

Creating Your First Real Test

Now that the test project is set up, you can create meaningful tests. Here's an example:

1. Create a Calculator Class in the API Project

// MathApp.API/Calculator.cs
namespace MathApp.API;

public class Calculator
{
    public int Add(int a, int b)
    {
        return a + b;
    }
    
    public int Subtract(int a, int b)
    {
        return a - b;
    }
    
    public int Multiply(int a, int b)
    {
        return a * b;
    }
    
    public double Divide(int a, int b)
    {
        if (b == 0)
            throw new DivideByZeroException("Cannot divide by zero");
        
        return (double)a / b;
    }
}

2. Create Tests for the Calculator

// MathApp.Tests/CalculatorTests.cs
using MathApp.API;

namespace MathApp.Tests;

public class CalculatorTests
{
    private readonly Calculator _calculator;
    
    public CalculatorTests()
    {
        _calculator = new Calculator();
    }
    
    [Fact]
    public void Add_TwoPositiveNumbers_ReturnsCorrectSum()
    {
        // Arrange
        int a = 5;
        int b = 3;
        
        // Act
        int result = _calculator.Add(a, b);
        
        // Assert
        Assert.Equal(8, result);
    }
    
    [Fact]
    public void Subtract_TwoNumbers_ReturnsCorrectDifference()
    {
        // Arrange
        int a = 10;
        int b = 4;
        
        // Act
        int result = _calculator.Subtract(a, b);
        
        // Assert
        Assert.Equal(6, result);
    }
    
    [Fact]
    public void Divide_ByZero_ThrowsDivideByZeroException()
    {
        // Arrange
        int a = 10;
        int b = 0;
        
        // Act & Assert
        Assert.Throws<DivideByZeroException>(() => _calculator.Divide(a, b));
    }
    
    [Theory]
    [InlineData(2, 3, 6)]
    [InlineData(5, 4, 20)]
    [InlineData(-3, 7, -21)]
    public void Multiply_VariousInputs_ReturnsCorrectProduct(int a, int b, int expected)
    {
        // Act
        int result = _calculator.Multiply(a, b);
        
        // Assert
        Assert.Equal(expected, result);
    }
}

Test Naming Conventions

Common Test Naming Pattern:

MethodName_StateUnderTest_ExpectedBehavior

Examples:

  • Add_TwoPositiveNumbers_ReturnsCorrectSum
  • Divide_ByZero_ThrowsDivideByZeroException
  • GetUser_WithValidId_ReturnsUser
  • CreateOrder_WithInvalidData_ThrowsValidationException

Arrange-Act-Assert Pattern

Structure tests using the AAA pattern:

  • Arrange: Set up test data and preconditions
  • Act: Execute the method or behavior being tested
  • Assert: Verify the expected outcome

Common xUnit Assertions

Assertion Purpose Example
Assert.Equal() Verifies two values are equal Assert.Equal(5, result)
Assert.NotEqual() Verifies two values are not equal Assert.NotEqual(0, count)
Assert.True() Verifies condition is true Assert.True(isValid)
Assert.False() Verifies condition is false Assert.False(hasErrors)
Assert.Null() Verifies object is null Assert.Null(user)
Assert.NotNull() Verifies object is not null Assert.NotNull(result)
Assert.Throws<T>() Verifies exception is thrown Assert.Throws<ArgumentException>(() => method())
Assert.Contains() Verifies collection contains item Assert.Contains(item, list)
Assert.Empty() Verifies collection is empty Assert.Empty(results)
Assert.InRange() Verifies value is within range Assert.InRange(score, 0, 100)

Key Concepts Summary

Solution File (.sln)
A container file that organizes multiple related projects, enabling collective management, building, and dependency tracking across the entire application.
xUnit
A free, open-source unit testing framework for .NET that provides attributes, assertions, and test execution capabilities. It's the modern successor to NUnit and is maintained by the .NET Foundation.
Test Project
A separate project dedicated to containing unit tests, isolated from production code but referencing the application projects it tests.
Project Reference
A link from one project to another that allows the first project to access types and members from the referenced project, essential for test projects to access application code.
[Fact] Attribute
An xUnit attribute that marks a method as a unit test with no parameters. Tests marked with [Fact] are discovered and executed by test runners.
[Theory] Attribute
An xUnit attribute for parameterized tests that can be run multiple times with different input data using [InlineData], [MemberData], or [ClassData] attributes.
Test Runner
A tool or component that discovers and executes unit tests. The .NET Test SDK provides test runner functionality through the dotnet test command.
Code Coverage
A measurement of how much of your code is executed during testing, helping identify untested code paths. Collected using tools like coverlet.collector.
Assertion
A statement in a test that verifies an expected outcome. If the assertion fails, the test fails, indicating a problem with the code under test.
Arrange-Act-Assert (AAA)
A common pattern for structuring unit tests: Arrange sets up test data, Act executes the method being tested, and Assert verifies the expected outcome.

Best Practices for Unit Testing

  • Test Independence: Each test should be independent and not rely on other tests
  • Clear Naming: Use descriptive test names that explain what is being tested
  • Single Responsibility: Each test should verify one specific behavior
  • Fast Execution: Tests should run quickly to encourage frequent execution
  • Maintainability: Write tests that are easy to understand and maintain
  • Comprehensive Coverage: Test both success and failure scenarios
  • Meaningful Assertions: Use appropriate assertions that clearly verify expected outcomes

With this foundation in place, you can now write meaningful tests to verify your application's behavior, catch bugs early, and maintain code quality through automated testing.
