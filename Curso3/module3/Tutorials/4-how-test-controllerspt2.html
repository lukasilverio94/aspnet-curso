Testing Controllers with the AAA Pattern

Unit tests for controllers verify that HTTP endpoints return the correct responses. We use the Arrange-Act-Assert pattern to structure our tests clearly and maintain consistency.

Testing the GetUser Method

Let's examine a complete test that verifies the controller returns the correct user when a valid ID is provided:

var okayResult = Assert.IsType<OkObjectResult>(result);
var returnedUser = Assert.IsType<User>(okayResult.Value);

Assert.Equal(expectedUserId, returnedUser.Id);
Assert.Equal(expectedUserName, returnedUser.Name);

The Assert Section Explained

The assert section verifies three critical aspects:

  1. Result Type: Confirms the result is an OkObjectResult
  2. Value Type: Verifies the value inside that result is a User object
  3. Property Values: Ensures the returned user has the expected ID and name properties

Each assertion is specific and provides clear diagnostic information if something fails.

Testing Error Conditions

Testing how your controller handles errors is just as important as testing success scenarios. Here's a test that verifies behavior when a user doesn't exist:

public void GetUser_WithInvalidId_ReturnsNotFound()
{
    // Arrange - Configure mock to return null (user not found)
    
    // Act - Call the GetUser method on controller
    
    // Assert - Verify NotFound result is returned
}

Line 40: The mock is configured to return null, simulating a scenario where the user wasn't found in the database.

Line 48: The assertion verifies that the controller returns a NotFound result, which translates to an HTTP 404 response.

Testing Business Services

Service layer tests validate business logic, data validation, and proper exception handling. Unlike controller tests, service tests focus on the core application logic rather than HTTP concerns.

Testing User Creation with Email Validation

The following test validates the service's user creation logic, including email uniqueness checks:

// Arrange
// Mock repository to indicate email doesn't exist
// Mock repository to return created user

// Act
var result = await userService.CreateUser(newUser);

// Assert
// Verify user was created with expected properties

Mocking Repository Dependencies

In this service test, the repository dependency is mocked with two different behaviors:

  1. Email Check: Configure the mock to return false, indicating the email doesn't already exist
  2. User Creation: Configure what the repository returns when creating the user

This approach allows testing the service's business logic without requiring an actual database connection.

Testing Exception Handling for Duplicate Emails

Services should throw appropriate exceptions when business rules are violated. Here's how to test that duplicate emails are properly rejected:

public async Task CreateUser_WithDuplicateEmail_ThrowsException()
{
    // Arrange
    // Mock repository to indicate email already exists
    
    // Act & Assert
    await Assert.ThrowsAsync<ArgumentException>(
        async () => await userService.CreateUser(duplicateUser)
    );
}

Line 52: Assert.ThrowsAsync serves a dual purpose—it both executes the method and verifies that the correct exception type (ArgumentException) is thrown.

This ensures the service properly enforces the business rule that email addresses must be unique.

Running and Reviewing Test Results

After writing tests, you need to execute them to verify your implementation works correctly. The .NET CLI provides straightforward commands for running tests.

Executing Tests with dotnet test

Open a terminal window in your solution directory and run:

dotnet test

This command discovers and executes all test methods in your solution. The test runner provides output showing:

  • Total number of tests executed
  • Number of passed tests
  • Number of failed tests (if any)
  • Execution time for each test

Expected Output: All tests should pass, confirming that both controller and service implementations work as expected. Green checkmarks or "Passed" indicators show successful test execution.

Using Test Explorer for Individual Tests

Visual Studio and Visual Studio Code provide a Test Explorer view that offers additional capabilities:

  • View all tests in a hierarchical structure
  • Run individual tests or groups of tests
  • Debug specific test failures
  • View detailed failure messages and stack traces
  • Re-run only failed tests

This visual interface makes it easy to isolate and debug specific test failures without running your entire test suite.

Key Testing Patterns and Best Practices

Arrange-Act-Assert (AAA) Pattern
A structured approach to writing tests with three distinct sections: setting up test data (Arrange), executing the code under test (Act), and verifying expected outcomes (Assert).
Mocking Dependencies
Creating test doubles for dependencies like repositories or external services, allowing you to test code in isolation without requiring actual database connections or external systems.
Testing Success Scenarios
Verifying that your code produces correct results when given valid inputs and when all dependencies behave normally.
Testing Error Conditions
Ensuring your code handles invalid inputs, missing data, and failure scenarios gracefully by returning appropriate error responses or throwing expected exceptions.
Specific Assertions
Writing assertions that verify exact expected outcomes rather than general conditions, providing clear diagnostic information when tests fail.
Isolated Tests
Each test should verify one specific behavior and be independent of other tests, allowing tests to run in any order without affecting results.
