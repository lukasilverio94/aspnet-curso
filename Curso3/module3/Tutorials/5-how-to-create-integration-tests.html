Integration Testing ASP.NET Core APIs with WebApplicationFactory

Complete guide to testing API endpoints from HTTP request to database response

Demonstration Overview

Integration tests validate that your API endpoints work correctly from HTTP request to database response. This demonstration covers:

  • Setting up integration tests using WebApplicationFactory
  • Testing complete API workflows end-to-end
  • Handling test databases effectively with in-memory providers
  • Creating a custom test class for API integration testing
  • Configuring dependency injection for test scenarios

What Are Integration Tests? Integration tests verify that multiple components of your application work together correctly. Unlike unit tests that test individual methods in isolation, integration tests validate the entire workflow from HTTP request, through controllers and services, down to the database and back.

Examining the ProductsController

Opening the Controller

Open the ProductsController.cs file to examine the endpoints that will be tested.

Standard CRUD Operations

using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using WebApplicationFactoryDemo.Data;
using WebApplicationFactoryDemo.Models;

namespace WebApplicationFactoryDemo.Controllers;

[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    private readonly AppDbContext _context;
    
    public ProductsController(AppDbContext context)
    {
        _context = context;
    }
    
    // GET: api/products
    [HttpGet]
    public async Task<ActionResult<IEnumerable<Product>>> GetProducts()
    {
        return await _context.Products.ToListAsync();
    }
    
    // GET: api/products/5
    [HttpGet("{id}")]
    public async Task<ActionResult<Product>> GetProduct(int id)
    {
        var product = await _context.Products.FindAsync(id);
        
        if (product == null)
        {
            return NotFound();
        }
        
        return product;
    }
    
    // POST: api/products
    [HttpPost]
    public async Task<ActionResult<Product>> CreateProduct(Product product)
    {
        _context.Products.Add(product);
        await _context.SaveChangesAsync();
        
        return CreatedAtAction(nameof(GetProduct), new { id = product.Id }, product);
    }
    
    // PUT: api/products/5
    [HttpPut("{id}")]
    public async Task<IActionResult> UpdateProduct(int id, Product product)
    {
        if (id != product.Id)
        {
            return BadRequest();
        }
        
        _context.Entry(product).State = EntityState.Modified;
        
        try
        {
            await _context.SaveChangesAsync();
        }
        catch (DbUpdateConcurrencyException)
        {
            if (!ProductExists(id))
            {
                return NotFound();
            }
            throw;
        }
        
        return NoContent();
    }
    
    // DELETE: api/products/5
    [HttpDelete("{id}")]
    public async Task<IActionResult> DeleteProduct(int id)
    {
        var product = await _context.Products.FindAsync(id);
        if (product == null)
        {
            return NotFound();
        }
        
        _context.Products.Remove(product);
        await _context.SaveChangesAsync();
        
        return NoContent();
    }
    
    private bool ProductExists(int id)
    {
        return _context.Products.Any(e => e.Id == id);
    }
}

Understanding IClassFixture

IClassFixture<WebApplicationFactory<Program>>: This interface tells xUnit to:

  • Create one instance of WebApplicationFactory for all tests in the class
  • Share the test server across multiple test methods
  • Dispose of resources properly after all tests complete
  • Improve test performance by reusing the test server

Program Class: The generic type parameter <Program> specifies the application's entry point, which WebApplicationFactory uses to configure the test server with the same services and middleware as the real application.

Private Fields and Constructor

Private HttpClient Field

private readonly HttpClient _client;

Stores the HTTP client used to make requests to the test server. This client is configured to communicate with the in-memory test server created by WebApplicationFactory.

Constructor

public ProductsControllerIntegrationTests(
    WebApplicationFactory<Program> factory)
{
    _client = factory.CreateClient();
}

Constructor Purpose:

  • Receives the WebApplicationFactory instance via dependency injection
  • Calls factory.CreateClient() to create an HttpClient
  • Stores the client in the private field for use in all test methods
  • Ensures each test method uses the same client connected to the same test server

Configuring a Custom WebApplicationFactory

Why Create a Custom Factory?

Important Note: To properly configure the in-memory database and override services for testing, you should create a custom WebApplicationFactory class rather than modifying the test class directly. This follows best practices and keeps test configuration separate from test logic.

Creating a Custom Factory Class

Create a new file named CustomWebApplicationFactory.cs in the test project:

using Microsoft.AspNetCore.Hosting;
using Microsoft.AspNetCore.Mvc.Testing;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.DependencyInjection;
using WebApplicationFactoryDemo.Data;

namespace ECommerceAPI.IntegrationTests;

public class CustomWebApplicationFactory<TProgram> 
    : WebApplicationFactory<TProgram> where TProgram : class
{
    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.ConfigureServices(services =>
        {
            // Remove the existing DbContext registration
            var descriptor = services.SingleOrDefault(
                d => d.ServiceType == typeof(DbContextOptions<AppDbContext>));
            
            if (descriptor != null)
            {
                services.Remove(descriptor);
            }
            
            // Add DbContext using in-memory database for testing
            services.AddDbContext<AppDbContext>(options =>
            {
                options.UseInMemoryDatabase("TestDatabase");
            });
            
            // Ensure the database is created
            var serviceProvider = services.BuildServiceProvider();
            using var scope = serviceProvider.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            db.Database.EnsureCreated();
        });
    }
}

Understanding ConfigureWebHost

Method Purpose

The ConfigureWebHost method allows you to modify the application's service configuration specifically for testing:

Step 1: Remove Existing DbContext
var descriptor = services.SingleOrDefault(
    d => d.ServiceType == typeof(DbContextOptions<AppDbContext>));

if (descriptor != null)
{
    services.Remove(descriptor);
}

Finds and removes the production database configuration so it can be replaced with the test configuration.

Step 2: Add In-Memory Database
services.AddDbContext<AppDbContext>(options =>
{
    options.UseInMemoryDatabase("TestDatabase");
});

Registers a new DbContext that uses an in-memory database named "TestDatabase".

Step 3: Ensure Database Creation
var serviceProvider = services.BuildServiceProvider();
using var scope = serviceProvider.CreateScope();
var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
db.Database.EnsureCreated();

Creates the in-memory database schema immediately, ensuring it's ready for tests.

Benefits of This Approach

  • Isolation: Tests don't affect production data
  • Speed: In-memory operations are much faster than disk-based databases
  • Simplicity: No need to manage database connections or cleanup
  • Independence: Each test can start with a clean database state
  • No External Dependencies: Tests run without requiring a database server

Integration Testing Key Concepts

Unit Tests vs Integration Tests

Unit Tests Integration Tests
Test individual methods in isolation Test complete workflows across components
Use mocks for dependencies Use real implementations (with test database)
Very fast execution (milliseconds) Slower execution (still fast with in-memory DB)
Test business logic Test request/response flow and integration points
Verify method output Verify HTTP status codes and response data
Focus on one class at a time Test multiple layers working together

What Integration Tests Validate

  1. HTTP Routing: Requests reach the correct controller actions
  2. Model Binding: Request data is properly converted to method parameters
  3. Validation: Data annotations and validation rules are enforced
  4. Authorization: Security policies are correctly applied
  5. Business Logic: Controllers, services, and repositories work together
  6. Database Operations: Data is correctly saved and retrieved
  7. Response Serialization: Data is properly formatted in responses
  8. Status Codes: Appropriate HTTP status codes are returned
  9. Error Handling: Exceptions are properly caught and handled

WebApplicationFactory Benefits

  • In-Memory Test Server: No need to deploy the application
  • Real HTTP Pipeline: Tests use the actual middleware and routing
  • Service Overrides: Easy to replace services for testing
  • Fast Execution: Runs much faster than deployed tests
  • Isolation: Each test class gets its own server instance
  • Configuration Control: Full control over application configuration

Integration Testing Best Practices

Test Organization

  • Separate Test Projects: Keep integration tests in their own project
  • Clear Naming: Use descriptive names indicating what's being tested
  • One Class Per Controller: Create one test class for each controller
  • Logical Grouping: Group related tests together

Test Data Management

  • Fresh Database: Start each test with a clean database state
  • Seed Required Data: Add any necessary test data in the test setup
  • Avoid Hard-Coded IDs: Use generated IDs when possible
  • Clean Up: Let the in-memory database be disposed automatically

Test Execution

  • Test Independence: Tests should not depend on each other
  • Idempotent Tests: Running tests multiple times should produce same results
  • Fast Execution: Keep integration tests reasonably fast
  • Clear Assertions: Verify both status codes and response content

Configuration

Best Practice: Always use a custom WebApplicationFactory class to configure services for testing. Do not override ConfigureWebHost directly in test classes, as this violates separation of concerns and makes tests harder to maintain.

Next Steps: Writing Integration Tests

Sample Integration Test Structure

With the setup complete, you can now write integration tests like this:

[Fact]
public async Task GetProducts_ReturnsSuccessAndProducts()
{
    // Arrange - setup is already done in constructor
    
    // Act
    var response = await _client.GetAsync("/api/products");
    
    // Assert
    response.EnsureSuccessStatusCode();
    var products = await response.Content.ReadFromJsonAsync<List<Product>>();
    Assert.NotNull(products);
}

[Fact]
public async Task CreateProduct_ValidProduct_ReturnsCreatedProduct()
{
    // Arrange
    var newProduct = new Product
    {
        Name = "Test Product",
        Price = 99.99m,
        Description = "Test Description"
    };
    
    // Act
    var response = await _client.PostAsJsonAsync("/api/products", newProduct);
    
    // Assert
    Assert.Equal(HttpStatusCode.Created, response.StatusCode);
    var createdProduct = await response.Content.ReadFromJsonAsync<Product>();
    Assert.NotNull(createdProduct);
    Assert.Equal(newProduct.Name, createdProduct.Name);
}

Common Test Scenarios

  • GET Requests: Verify data retrieval works correctly
  • POST Requests: Test resource creation and validation
  • PUT Requests: Verify updates work properly
  • DELETE Requests: Ensure deletions function correctly
  • Error Cases: Test 404, 400, and other error responses
  • Validation: Verify validation rules are enforced
  • Authentication: Test secured endpoints (if applicable)

Key Concepts Summary

Integration Tests
Tests that validate multiple components working together, from HTTP request through the entire application stack to the database and back, ensuring the complete workflow functions correctly.
WebApplicationFactory
A class that creates an in-memory test server for ASP.NET Core applications, allowing integration tests to make HTTP requests without deploying the application.
IClassFixture
An xUnit interface that creates one shared instance of a class for all tests in a test class, improving performance by reusing expensive resources like test servers.
In-Memory Database
A database provider that stores data in memory rather than on disk, providing fast test execution without requiring a real database server or affecting production data.
ConfigureWebHost
A method in WebApplicationFactory that allows you to modify service registrations and configuration specifically for testing, such as replacing the production database with an in-memory database.
HttpClient
A class for making HTTP requests. In integration tests, the client is created by WebApplicationFactory and is configured to communicate with the in-memory test server.
CRUD Operations
Create, Read, Update, Delete - the four basic database operations that are commonly exposed as HTTP endpoints (POST, GET, PUT, DELETE) in REST APIs.
Custom WebApplicationFactory
A derived class that extends WebApplicationFactory to provide custom configuration for tests, such as replacing services or adding test-specific middleware.
