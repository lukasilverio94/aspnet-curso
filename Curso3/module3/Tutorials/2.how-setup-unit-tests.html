Implementing the Calculator Class

namespace MathApp.API;

public class Calculator
{
    public int Add(int a, int b)
    {
        return a + b;
    }
    
    public int Subtract(int a, int b)
    {
        return a - b;
    }
    
    public double Divide(int a, int b)
    {
        if (b == 0)
            throw new DivideByZeroException("Cannot divide by zero");
        
        return (double)a / b;
    }
    
    public int Multiply(int a, int b)
    {
        return a * b;
    }
}

Writing Your First Meaningful Unit Test

Opening the Test File

Adding Using Statement

using MathApp.API;

Note: If you configured global usings in the project file, you may not need to add this using statement to every file. However, it's shown here for clarity.

Replacing the Default Test

Replace the default test with a meaningful test for the Calculator class:

using MathApp.API;

namespace MathApp.Tests;

public class CalculatorTests
{
    [Fact]
    public void Add_TwoNumbers_ReturnsCorrectSum()
    {
        // Arrange
        var calculator = new Calculator();
        int a = 5;
        int b = 3;
        
        // Act
        int result = calculator.Add(a, b);
        
        // Assert
        Assert.Equal(8, result);
    }
}

Understanding the Arrange-Act-Assert Pattern

The Arrange-Act-Assert (AAA) Pattern: A common structure for organizing unit tests that makes them clear, consistent, and maintainable.

Arrange

Purpose: Set up test data and preconditions

var calculator = new Calculator();
int a = 5;
int b = 3;

Creates a Calculator instance and defines input values for the test.

Act

Purpose: Execute the method being tested

int result = calculator.Add(a, b);

Calls the Add method with the test values and captures the result.

Assert

Purpose: Verify the expected outcome

Assert.Equal(8, result);

Verifies that the result equals the expected value of 8.

Benefits of the AAA Pattern

  • Clarity: Each section has a clear, single purpose
  • Consistency: Tests follow a predictable structure
  • Readability: Easy for other developers to understand
  • Maintainability: Changes are easy to locate and implement

Adding More Test Scenarios

Testing Multiple Scenarios

Add additional tests to demonstrate different testing scenarios including normal operations and exception handling:

using MathApp.API;

namespace MathApp.Tests;

public class CalculatorTests
{
    [Fact]
    public void Add_TwoNumbers_ReturnsCorrectSum()
    {
        // Arrange
        var calculator = new Calculator();
        int a = 5;
        int b = 3;
        
        // Act
        int result = calculator.Add(a, b);
        
        // Assert
        Assert.Equal(8, result);
    }
    
    [Fact]
    public void Subtract_TwoNumbers_ReturnsCorrectDifference()
    {
        // Arrange
        var calculator = new Calculator();
        int a = 10;
        int b = 4;
        
        // Act
        int result = calculator.Subtract(a, b);
        
        // Assert
        Assert.Equal(6, result);
    }
    
    [Fact]
    public void Divide_ByZero_ThrowsDivideByZeroException()
    {
        // Arrange
        var calculator = new Calculator();
        int a = 10;
        int b = 0;
        
        // Act & Assert
        Assert.Throws<DivideByZeroException>(() => calculator.Divide(a, b));
    }
}

Understanding Each Test

1. Add Test

Purpose: Verifies that the Add method correctly sums two numbers.

Expected: 5 + 3 = 8

Pattern: Standard AAA pattern with separate sections

2. Subtract Test

Purpose: Verifies that the Subtract method correctly calculates the difference.

Expected: 10 - 4 = 6

Pattern: Standard AAA pattern demonstrating consistent structure

3. Exception Test

Purpose: Verifies that dividing by zero throws the correct exception.

Expected: DivideByZeroException is thrown

Pattern: Act and Assert phases are combined when testing exceptions

Testing Exceptions with Assert.Throws
Assert.Throws<DivideByZeroException>(() => calculator.Divide(a, b));

This syntax uses a lambda expression to execute the code that should throw an exception. If the expected exception is thrown, the test passes. If no exception or a different exception is thrown, the test fails.

    Assert.Throws<DivideByZeroException>(() => calculator.Divide(a, b));

Unit Testing Best Practices

Test Organization

Practice Description Example
Descriptive Names Test names should describe what is being tested Add_TwoNumbers_ReturnsCorrectSum
One Class Per Feature Group related tests in the same class CalculatorTests for all Calculator tests
AAA Pattern Use Arrange-Act-Assert structure consistently Clear sections in every test
Test Independence Each test should run independently Create new instances in each test

What to Test

  • Happy Path: Test normal, expected behavior
  • Edge Cases: Test boundary conditions (zero, negative numbers, null, empty)
  • Exception Scenarios: Verify proper error handling
  • Business Logic: Test critical business rules
  • State Changes: Verify objects are modified correctly

Test Characteristics

Good Tests are FIRST:

Fast
Tests should execute quickly (milliseconds, not seconds)
Independent
Tests should not depend on each other or external state
Repeatable
Tests should produce the same results every time
Self-Validating
Tests should have clear pass/fail outcomes without manual verification
Timely
Write tests at the right time (ideally before or with the code)

Common xUnit Assertions Reference

Assertion Use Case Example from This Tutorial
Assert.Equal(expected, actual) Verify values are equal Assert.Equal(8, result)
Assert.NotEqual(expected, actual) Verify values are not equal Testing for changed values
Assert.True(condition) Verify condition is true Assert.True(result > 0)
Assert.False(condition) Verify condition is false Assert.False(result < 0)
Assert.Null(object) Verify object is null Testing method returns null
Assert.NotNull(object) Verify object is not null Testing object creation
Assert.Throws<T>(action) Verify exception is thrown Assert.Throws<DivideByZeroException>(() => calculator.Divide(a, b))
Assert.Contains(item, collection) Verify collection contains item Testing list operations
Assert.Empty(collection) Verify collection is empty Testing cleared collections
Assert.InRange(actual, low, high) Verify value is within range Testing calculated values

What You Can Test

public class UserServiceTests

    public void CreateUser_ValidData_ReturnsUser()

public class ProductsControllerTests

public class ValidationHelperTests

Key Concepts Summary

Arrange-Act-Assert (AAA) Pattern
A structural pattern for organizing unit tests into three clear sections: Arrange sets up test data, Act executes the method under test, and Assert verifies the expected outcome.
[Fact] Attribute
An xUnit attribute that marks a parameterless method as a unit test. Tests marked with [Fact] are automatically discovered and executed by test runners.
Test Method Naming
A convention for naming test methods that describes what is being tested, the conditions, and the expected outcome, such as MethodName_Scenario_ExpectedResult.
Assert.Equal
An xUnit assertion method that verifies two values are equal. If they're not equal, the test fails with a message showing the expected and actual values.
Assert.Throws<T>
An xUnit assertion method that verifies a specific exception type is thrown when executing code. The Act and Assert phases are typically combined when testing exceptions.
Test Independence
The principle that each test should run independently without relying on other tests or maintaining shared state, ensuring tests can run in any order.
Test Failure Output
Detailed information provided by the test runner when a test fails, including which test failed, expected vs actual values, and a stack trace for debugging.
Test Discovery
The process by which test runners automatically find and identify test methods in a project by looking for test attributes like [Fact] and [Theory].
