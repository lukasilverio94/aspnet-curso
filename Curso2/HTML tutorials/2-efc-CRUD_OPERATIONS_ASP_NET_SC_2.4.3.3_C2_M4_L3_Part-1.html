Implementing CRUD Operations with Service Layer Architecture

Overview

Building CRUD (Create, Read, Update, Delete) operations correctly separates hobbyist code from production-ready applications. This tutorial demonstrates how to implement CRUD operations using Service Layer Architecture with Entity Framework Core, following the same patterns used in enterprise applications handling millions of transactions daily.

What You'll Learn: This tutorial covers creating a complete CRUD implementation with proper separation of concerns, including entity models, repository interfaces, service layer architecture, dependency injection, and business validation.

Project Structure Setup

Creating the Folder Structure

Begin with an existing Web API project in Visual Studio Code. Create three key folders to organize your code:

YourProject/
├── Models/          (Entity classes)
├── Repositories/    (Data access layer)
└── Services/        (Business logic layer)
  • Models: Contains entity classes that represent database tables
  • Repositories: Contains data access interfaces and implementations
  • Services: Contains business logic and validation

Best Practice: This three-layer architecture provides clear separation of concerns, making your code more maintainable, testable, and scalable.

Creating the Product Entity

Step 1: Create the Entity File

In the Models folder, create a new file named Product.cs:

  1. Right-click the Models folder
  2. Select "New File"
  3. Type Product.cs as the filename

Step 2: Define the Product Entity

public class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public decimal Price { get; set; }
    public string Description { get; set; } = string.Empty;
}

Property Breakdown

Id
Integer property serving as the primary key for database identification
Name
String property for the product name, initialized with string.Empty to avoid null reference warnings
Price
Decimal property for the product cost, providing precision for monetary values
Description
String property for additional product details, initialized with string.Empty

Note: Using string.Empty as default values helps avoid null reference warnings in modern C# with nullable reference types enabled.

Creating the Repository Interface

Step 1: Create the Interface File

In the Repositories folder, create a new file named IProductRepository.cs:

  1. Right-click the Repositories folder
  2. Select "New File"
  3. Type IProductRepository.cs as the filename

Step 2: Define the Repository Interface

public interface IProductRepository
{
    Task<Product?> GetByIdAsync(int id);
    Task<IEnumerable<Product>> GetAllAsync();
    Task<Product> CreateAsync(Product product);
    Task<Product> UpdateAsync(Product product);
    Task DeleteAsync(int id);
}

Repository Methods Explained

GetByIdAsync(int id)
Retrieves a single product by its ID. Returns nullable Product to handle cases where the product doesn't exist.
GetAllAsync()
Retrieves all products from the database. Returns an enumerable collection of products.
CreateAsync(Product product)
Adds a new product to the database. Returns the created product with its generated ID.
UpdateAsync(Product product)
Modifies an existing product in the database. Returns the updated product.
DeleteAsync(int id)
Removes a product from the database by its ID. Returns Task for asynchronous operation completion.

Why Async Methods? All methods are asynchronous to support scalable applications. Asynchronous operations prevent blocking threads during database access, allowing the application to handle more concurrent requests efficiently.

Creating the Service Interface

Step 1: Create the Service Interface File

In the Services folder, create a new file named IProductService.cs:

  1. Right-click the Services folder
  2. Select "New File"
  3. Type IProductService.cs as the filename

Step 2: Define the Service Interface

public interface IProductService
{
    Task<Product?> GetProductAsync(int id);
    Task<IEnumerable<Product>> GetAllProductsAsync();
    Task<Product> CreateProductAsync(Product product);
    Task<Product> UpdateProductAsync(Product product);
    Task DeleteProductAsync(int id);
}

Service vs Repository: The service interface mirrors the repository interface but focuses on business operations rather than data access. This separation allows you to add validation, business rules, logging, and other logic without affecting the data access layer.

Implementing the Service Class

Step 1: Create the Service Implementation File

In the Services folder, create a new file named ProductService.cs:

  1. Right-click the Services folder
  2. Select "New File"
  3. Type ProductService.cs as the filename

Step 2: Implement the Service Class with Dependency Injection

public class ProductService : IProductService
{
    private readonly IProductRepository _repository;

    public ProductService(IProductRepository repository)
    {
        _repository = repository;
    }

    // Methods will be implemented below
}

Understanding Dependency Injection

The service class uses constructor injection to receive the IProductRepository interface. This pattern provides several benefits:

  • Testability: Allows substituting mock repositories during unit testing
  • Loose Coupling: Service depends on the interface, not concrete implementation
  • Flexibility: Easy to swap repository implementations without changing service code
  • Inversion of Control: Dependencies are provided externally rather than created internally

Implementing the Create Method with Validation

Create Product Method

public async Task<Product> CreateProductAsync(Product product)
{
    // Validate product name
    if (string.IsNullOrWhiteSpace(product.Name))
    {
        throw new ArgumentException("Product name cannot be empty", nameof(product.Name));
    }

    // Validate product price
    if (product.Price <= 0)
    {
        throw new ArgumentException("Product price must be positive", nameof(product.Price));
    }

    // Call repository to create the product
    return await _repository.CreateAsync(product);
}

Validation Logic Breakdown

The create method implements business validation before calling the repository:

Name Validation

Checks if the product name is null, empty, or contains only whitespace. Throws an ArgumentException with a descriptive message if validation fails.

Price Validation

Ensures the price is a positive value. Throws an ArgumentException if the price is zero or negative.

Repository Call

Only after all validation passes does the method call the repository's CreateAsync method to persist the product to the database.

Separation of Concerns: Business validation logic resides in the service layer, not the repository. This keeps data access code simple and focused on database operations while centralizing business rules in the service layer.

Implementing Read Operations

Get Product by ID Method

public async Task<Product?> GetProductAsync(int id)
{
    // Validate ID
    if (id <= 0)
    {
        throw new ArgumentException("Product ID must be positive", nameof(id));
    }

    // Call repository to retrieve the product
    return await _repository.GetByIdAsync(id);
}

Get All Products Method

public async Task<IEnumerable<Product>> GetAllProductsAsync()
{
    // Call repository to retrieve all products
    return await _repository.GetAllAsync();
}

Read Operations Explained

GetProductAsync Validation

Validates that the ID is a positive integer before calling the repository. This prevents unnecessary database queries for invalid IDs and provides clear error messages to calling code.

GetAllProductsAsync Simplicity

The get all products method is simpler since it doesn't require validation. However, in real-world applications, you might add additional logic here such as:

  • Filtering products by category or status
  • Implementing pagination for large datasets
  • Applying sorting based on various criteria
  • Caching frequently accessed product lists

Performance Consideration: For applications with large product catalogs, consider implementing pagination in the GetAllProductsAsync method to avoid loading excessive data into memory.

Benefits of Service Layer Architecture

Key Advantages

Separation of Concerns
Business logic is separated from data access, making code more maintainable and easier to understand. Each layer has a clear, focused responsibility.
Testability
Services can be tested independently by mocking the repository interface. This enables comprehensive unit testing without requiring database access.
Reusability
Business logic in the service layer can be reused across different controllers, APIs, or even different applications.
Maintainability
Changes to business rules only require updating the service layer. Data access logic remains unchanged, reducing the risk of introducing bugs.
Scalability
Asynchronous methods support high-concurrency scenarios. The architecture can easily accommodate caching, distributed transactions, or microservices patterns.
Flexibility
Repository implementations can be swapped without changing service code. This allows moving from Entity Framework to Dapper, or from SQL Server to PostgreSQL, with minimal code changes.

CRUD Implementation Best Practices

Validation Placement

Always place business validation in the service layer, not the repository. Repositories should focus solely on data access operations.

Async/Await Patterns

Use async/await consistently throughout the call chain from controller to service to repository. This maximizes scalability and prevents thread blocking.

Error Handling

Throw meaningful exceptions with descriptive messages. Include parameter names in ArgumentException constructors to help debugging.

Dependency Injection

Always inject dependencies through constructors rather than creating instances directly. This supports testing and follows SOLID principles.

Interface-First Design

Define interfaces before implementations. This encourages thinking about contracts and makes it easier to create mock implementations for testing.

Nullable Reference Types

Use nullable annotations appropriately (Product?) to indicate when methods might return null, helping prevent null reference exceptions.
