Implementing Update, Delete, and Unit Testing for CRUD Operations

Overview

This tutorial completes the CRUD implementation by adding update and delete operations, then demonstrates how to implement comprehensive unit testing using xUnit and Moq. You'll learn how to validate business rules, implement proper testing patterns, and verify service logic in isolation from the database.

Implementing the Update Operation

Update Product Method

public async Task<Product> UpdateProductAsync(Product product)
{
    // Validate product ID
    if (product.Id <= 0)
    {
        throw new ArgumentException("Product ID must be positive", nameof(product.Id));
    }

    // Validate product name
    if (string.IsNullOrWhiteSpace(product.Name))
    {
        throw new ArgumentException("Product name cannot be empty", nameof(product.Name));
    }

    // Validate product price
    if (product.Price <= 0)
    {
        throw new ArgumentException("Product price must be positive", nameof(product.Price));
    }

    // Call repository to update the product
    return await _repository.UpdateAsync(product);
}

Update Method Validation Breakdown

ID Validation

The update method includes an additional validation check not present in the create method: ensuring the product ID is valid. This check verifies that the ID is a positive integer, confirming we're updating an existing product record rather than accidentally creating a new one.

Name and Price Validation

The update method includes the same validation as the create method for name and price. This ensures data consistency and business rule enforcement regardless of whether you're creating or updating a product.

Repository Call

After all validations pass, the method calls the repository's UpdateAsync method to persist the changes to the database.

Validation Consistency: Update operations require the same business rule validation as create operations, plus additional checks to ensure you're modifying an existing record. This consistency prevents invalid data from entering your system through any entry point.

Implementing the Delete Operation

Delete Product Method

public async Task DeleteProductAsync(int id)
{
    // Validate ID
    if (id <= 0)
    {
        throw new ArgumentException("Product ID must be positive", nameof(id));
    }

    // Call repository to delete the product
    await _repository.DeleteAsync(id);
}

Delete Method Explained

The delete method validates the ID parameter and then calls the repository to remove the product. While this implementation is straightforward, production applications often require additional business logic.

Production Considerations for Delete Operations

In real-world applications, you might add several enhancements to the delete operation:

Existence Verification

Check if the product exists before attempting deletion, providing meaningful error messages if the product is not found.

Referential Integrity Checks

Verify if the product can be safely deleted by checking for related records such as orders, reviews, or inventory transactions. Prevent deletion of products that are referenced by other entities.

Soft Delete Implementation

Instead of permanently removing records, implement soft delete functionality by marking products as inactive or deleted. This preserves historical data and allows for potential recovery.

Cascading Operations

Handle related data appropriately, such as removing associated images, clearing cache entries, or triggering notifications to dependent systems.

Data Integrity: Always consider the broader implications of delete operations. In many business scenarios, soft deletes are preferred over hard deletes to maintain audit trails and historical records.

Creating the Test Class Structure

Test Class with Constructor

public class ProductServiceTests
{
    private readonly Mock<IProductRepository> _mockRepository;
    private readonly ProductService _productService;

    public ProductServiceTests()
    {
        _mockRepository = new Mock<IProductRepository>();
        _productService = new ProductService(_mockRepository.Object);
    }

    // Test methods will be added here
}

Test Class Components Explained

Mock Repository Field

The _mockRepository field creates a mock implementation of IProductRepository. This mock allows you to control what the repository returns and verify that it's called correctly, without requiring a real database.

Product Service Field

The _productService field holds the instance of the service being tested. It receives the mock repository through dependency injection.

Constructor Setup

The constructor instantiates the mock repository and product service. This setup ensures that each test gets a fresh, isolated environment, preventing tests from affecting each other.

Test Isolation: xUnit creates a new instance of the test class for each test method, ensuring complete isolation. The constructor runs before each test, providing a clean slate every time.

Implementing the Create Product Test

Complete Test Method

[Fact]
public async Task CreateProductAsync_ValidProduct_ReturnsCreatedProduct()
{
    // Arrange
    var testProduct = new Product
    {
        Id = 1,
        Name = "Test Product",
        Price = 99.99m,
        Description = "Test Description"
    };

    _mockRepository
        .Setup(repo => repo.CreateAsync(It.IsAny<Product>()))
        .ReturnsAsync(testProduct);

    // Act
    var result = await _productService.CreateProductAsync(testProduct);

    // Assert
    Assert.NotNull(result);
    Assert.Equal("Test Product", result.Name);
    _mockRepository.Verify(
        repo => repo.CreateAsync(It.IsAny<Product>()), 
        Times.Once
    );
}

Understanding the Arrange-Act-Assert Pattern

Arrange Section

The Arrange section sets up the test environment:

  • Creates a test product with sample data
  • Configures the mock repository to return the test product when CreateAsync is called
  • Uses It.IsAny<Product>() to accept any product parameter

Act Section

The Act section executes the code being tested by calling the service method with the test product.

Assert Section

The Assert section verifies the results:

  • Assert.NotNull(result): Confirms the method returned a result
  • Assert.Equal("Test Product", result.Name): Verifies the returned product has the correct name
  • _mockRepository.Verify(..., Times.Once): Confirms the repository method was called exactly one time

Power of Mocking: This test demonstrates the value of dependency injection and mocking. You're testing the service logic in complete isolation from the actual database, making tests fast, reliable, and independent of external dependencies.

Benefits of Comprehensive Unit Testing

Fast Execution
Tests run in milliseconds without database connections, allowing you to run hundreds or thousands of tests quickly during development.
Isolation and Reliability
Tests don't depend on external systems like databases or APIs. They produce consistent results regardless of environment, preventing flaky tests.
Early Bug Detection
Unit tests catch logic errors immediately during development, before code reaches integration testing or production.
Documentation
Well-written tests serve as living documentation showing how the code should behave and how to use the APIs.
Refactoring Confidence
Comprehensive test coverage allows you to refactor code safely, knowing that tests will catch any behavioral changes.
Design Feedback
Difficulty writing tests often indicates design problems. If a class is hard to test, it's likely doing too much or has tight coupling.

Additional Tests to Implement

Validation Tests

Test that validation logic works correctly by attempting to create or update products with invalid data:

  • Test creating a product with an empty name
  • Test creating a product with zero or negative price
  • Test updating a product with an invalid ID
  • Verify that appropriate exceptions are thrown with correct messages

Read Operation Tests

Test the retrieval methods to ensure they return correct data:

  • Test GetProductAsync with valid and invalid IDs
  • Test GetAllProductsAsync returns all products
  • Test behavior when products don't exist (null handling)

Update and Delete Tests

Verify update and delete operations work as expected:

  • Test successful product updates with valid data
  • Test update validation failures
  • Test successful product deletion
  • Test deletion with invalid IDs

Repository Interaction Tests

Verify the service calls repository methods correctly:

  • Confirm methods are called with expected parameters
  • Verify methods are called the correct number of times
  • Test that service passes data to repository unchanged (when appropriate)

Unit Testing Best Practices

Test Naming Conventions

Use descriptive test names that follow the pattern: MethodName_Scenario_ExpectedResult. For example: CreateProductAsync_ValidProduct_ReturnsCreatedProduct.

One Assertion per Test Concept

While multiple Assert statements are acceptable, each test should verify one logical concept. Don't try to test create, update, and delete in a single test method.

Arrange-Act-Assert Pattern

Always structure tests with clear Arrange, Act, and Assert sections. This makes tests easier to read and maintain.

Use Meaningful Test Data

Choose test data that makes tests self-documenting. Use descriptive names like "Test Product" rather than generic values.

Test Both Happy and Sad Paths

Write tests for successful scenarios (happy path) and error scenarios (sad path). Verify that your code handles failures gracefully.

Mock Verification

Always verify that mocked dependencies are called correctly using Verify() methods. This ensures your service interacts with dependencies as expected.

Key Principles Review

Remember These Core Principles:

Use Dependency Injection for Testability

Inject dependencies through constructors rather than creating instances directly. This enables substituting mock implementations during testing and promotes loose coupling.

Validate Business Rules in the Service Layer

Keep all business validation logic in the service layer, not in repositories or controllers. This centralizes rules and makes them easier to test and maintain.

Keep Repositories Focused on Data Access

Repositories should only handle database operations without business logic. This separation allows you to change data access strategies without affecting business rules.

Write Unit Tests that Verify Logic in Isolation

Use mocking to test services independently of databases and external systems. This produces fast, reliable tests that catch logic errors early.
