## Advanced Configuration Validation

### Custom Validation Logic

While data annotation attributes handle many validation scenarios, complex applications often require custom validation logic that examines multiple properties or performs external validation checks. ASP.NET Core supports custom validation through the `IValidateOptions<T>` interface.

Custom validation classes implement logic that goes beyond simple property checks. For example, you might validate that a database connection string is accessible, API endpoints are reachable, or configuration combinations are logically consistent.

Consider a scenario where your weather API configuration requires different validation rules based on the selected provider. A custom validator can implement business rules like ensuring premium features are only enabled when using paid API tiers, or validating that caching timeouts are appropriate for the selected data refresh intervals.

```cs
// Implements custom validation for WeatherApiOptions using IValidateOptions<T>
public class WeatherApiOptionsValidator : IValidateOptions<WeatherApiOptions>
{
    public ValidateOptionsResult Validate(string name, WeatherApiOptions options)
    {
        var failures = new List<string>();
        // Validate API key format based on provider
        if (options.Provider == "WeatherAPI" && !options.ApiKey.StartsWith("wa_"))
        {
            failures.Add("WeatherAPI keys must start with 'wa_' prefix");
        }
        // Validate timeout consistency
        if (options.EnableCaching && options.CacheTimeoutMinutes > options.TimeoutSeconds * 60)
        {
            failures.Add("Cache timeout cannot exceed API timeout");
        }
        return failures.Count > 0 
            ? ValidateOptionsResult.Fail(failures)
            : ValidateOptionsResult.Success;
    }
}

```

Custom validators are registered with the dependency injection container alongside your options configuration, ensuring they execute during the validation process.

### Conditional Validation

Advanced applications often need different validation rules based on the runtime environment or configuration context. Conditional validation allows you to apply different validation logic for development, staging, and production environments.

Environment-specific validation is beneficial when development environments use mock services or relaxed security requirements, while production environments enforce strict validation rules. You can implement conditional logic within your validators or register different validator implementations based on the current environment.

This approach enables scenarios like allowing localhost URLs in development while requiring HTTPS endpoints in production, or accepting test API keys during development while enforcing complex key validation in production environments.

## Runtime Configuration Changes

### IOptionsMonitor for Dynamic Updates

Traditional options injection with `IOptions<T>` provides a snapshot of configuration values at application startup. However, modern applications often need to respond to configuration changes without requiring application restarts. The `IOptionsMonitor<T>` interface enables real-time configuration monitoring and updates.

`IOptionsMonitor<T>` automatically detects changes to configuration sources like JSON files and provides updated configuration values to your application components. This capability is essential for applications that need to adjust behavior based on feature flags, update API endpoints, or modify timeout values without downtime.

The monitor interface provides several methods for accessing configuration: CurrentValue for immediate access to current settings, Get(string name) for named options scenarios, and OnChange for registering callbacks that execute when configuration changes occur.

```cs
public class WeatherService
{
    private readonly IOptionsMonitor<WeatherApiOptions> _optionsMonitor;
    private WeatherApiOptions _currentOptions;
    public WeatherService(IOptionsMonitor<WeatherApiOptions> optionsMonitor)
    {
        _optionsMonitor = optionsMonitor;
        _currentOptions = _optionsMonitor.CurrentValue;
        // Register for configuration changes
        _optionsMonitor.OnChange(options => 
        {
            _currentOptions = options;
            ReconfigureHttpClient();
        });
    }
    private void ReconfigureHttpClient()
    {
        // Update HTTP client configuration based on new options
        // This allows runtime adaptation to configuration changes
    }
}
```

### Change Notifications and Callbacks

Configuration change notifications enable applications to respond intelligently to updated settings. Rather than simply using new values, applications can implement sophisticated responses like clearing caches, reconnecting to services, or updating internal state.

Change callbacks can implement complex logic, such as graceful service transitions, where the application continues using existing connections while gradually shifting to new configuration values. This approach minimizes disruption when configuration changes occur in production environments.

Effective change handling also includes error recovery mechanisms for scenarios where new configuration values are invalid or cause service failures. Applications can implement fallback strategies that revert to previous configuration values when new settings cause problems.

## Custom Configuration Providers

### Creating Custom Providers

ASP.NET Core's provider-based configuration system allows you to create custom configuration sources that integrate seamlessly with the built-in configuration system. Custom providers enable scenarios like loading configuration from databases, external APIs, or specialized file formats.

Custom configuration providers implement the IConfigurationProvider interface and are typically paired with a corresponding IConfigurationSource implementation. The provider handles the actual configuration loading logic, while the source integrates the provider into the configuration system.

Database configuration providers are common in enterprise scenarios where configuration values must be managed through administrative interfaces or shared across multiple application instances. These providers can implement caching strategies, change notifications, and fallback mechanisms for scenarios where the database is unavailable.

External API providers enable scenarios like loading configuration from centralized configuration services, feature flag systems, or cloud-based configuration management platforms. These providers often implement retry logic, authentication, and secure communication protocols.

### Provider Integration Patterns

Effective custom providers implement patterns that ensure reliable configuration loading and graceful error handling. Provider implementations should consider startup order, dependency relationships, and fallback strategies when external sources are unavailable.

Configuration provider composition allows combining multiple custom providers with built-in providers to create sophisticated configuration hierarchies. For example, an application might use JSON files for default values, database providers for environment-specific settings, and API providers for feature flags.

Provider integration also involves considering performance characteristics, especially for providers that access external resources. Implementing appropriate caching, connection pooling, and timeout strategies ensures that configuration loading doesn't negatively impact application startup or runtime performance.

## Complex Configuration Scenarios

### Multi-Tenant Configuration

Multi-tenant applications require configuration systems that can provide different settings for different tenants while maintaining performance and security isolation. Advanced configuration techniques enable tenant-specific settings without duplicating configuration infrastructure.

Tenant-specific configuration often involves hierarchical configuration strategies where tenant-specific values override global defaults. This approach minimizes configuration duplication while allowing fine-grained customization for individual tenants.

Named options provide one approach for multi-tenant scenarios, where each tenant has a named configuration instance. The options factory pattern enables the dynamic creation of tenant-specific configuration objects based on runtime context, such as subdomain, authentication claims, or request headers.
```cs
public class TenantWeatherApiOptions : WeatherApiOptions
{
    public string TenantId { get; set; } = string.Empty;
    public Dictionary<string, string> TenantSpecificSettings { get; set; } = new();
}
// Usage in a service
public class TenantWeatherService
{
    public async Task<WeatherData> GetWeatherAsync(string tenantId)
    {
        var tenantOptions = _optionsFactory.Create($"tenant:{tenantId}");
        // Use tenant-specific configuration
    }
}
```


### Configuration Composition

Large applications often require composing a configuration from multiple sources with complex precedence rules and dependency relationships. Advanced composition techniques enable sophisticated configuration architectures that remain maintainable and testable.

Configuration sections can be composed from multiple providers, allowing different aspects of configuration to come from different sources. For example, database settings come from secure key vaults, feature flags from external APIs, and UI customization settings from JSON files.

Conditional configuration loading enables scenarios where configuration sources are selected based on runtime conditions, environment variables, or other contextual information. This approach supports advanced deployment patterns where the same application binary adapts to different environments based on available configuration sources.

## Configuration Testing Strategies

### Unit Testing Configuration

Professional applications require comprehensive testing strategies for configuration logic, including validation, binding, and runtime behavior. Configuration testing ensures that applications behave correctly across different configuration scenarios and environments.

Unit testing configuration involves testing options classes in isolation, validating that binding logic works correctly, and ensuring that validation rules catch expected error conditions. Mock configuration providers enable testing scenarios where external configuration sources behave unexpectedly.

Integration testing verifies that the configuration works correctly within the whole application context, including dependency injection, validation execution order, and interaction with other application components.

```cs
[Test]
public void WeatherApiOptions_ValidatesCorrectly()
{
    var options = new WeatherApiOptions
    {
        ApiKey = "short", // Too short
        BaseUrl = "invalid-url", // Invalid URL
        TimeoutSeconds = 200 // Too high
    };
    var context = new ValidationContext(options);
    var results = new List<ValidationResult>();
    
    var isValid = Validator.TryValidateObject(options, context, results, true);
    
    Assert.False(isValid);
    Assert.Equal(3, results.Count);
}

```

### Configuration Integration Testing

Integration testing for configuration involves verifying that the complete configuration system works correctly in realistic scenarios. This includes testing configuration precedence, provider integration, validation execution, and error handling.

Configuration integration tests often use test-specific configuration sources to ensure consistent, repeatable test conditions. Test containers, in-memory databases, or mock external services provide controlled environments for testing configuration behavior.

Automated testing should include scenarios for invalid configuration, missing configuration sources, and configuration changes during application runtime. These tests ensure that applications handle configuration problems gracefully rather than failing unpredictably.

## Performance and Optimization

### Configuration Caching Strategies

Configuration access patterns significantly impact application performance, especially for frequently accessed settings or configurations requiring expensive computation or external service calls. Effective caching strategies balance performance with the need for timely configuration updates.

Built-in configuration caching occurs automatically for most scenarios, but custom providers and complex configuration scenarios may require explicit caching implementations. Memory, distributed, and local caching strategies each provide different trade-offs between performance, consistency, and memory usage.

Configuration change invalidation ensures that the cached configuration remains current when underlying sources change. Implementing appropriate cache invalidation strategies prevents applications from using stale configuration while maintaining performance benefits.

### Lazy Loading and Initialization

Large applications with extensive configuration can benefit from lazy loading strategies that defer configuration loading until it's needed. This approach reduces application startup time and memory usage for configuration that may not be used in all scenarios.

Lazy configuration loading requires careful consideration of error handling, since configuration errors may not be discovered until runtime rather than during application startup. Implementing appropriate fallback strategies and error recovery mechanisms ensures that lazy loading doesn't compromise application reliability.

Configuration initialization patterns can implement sophisticated loading strategies such as parallel loading for independent configuration sections, progressive loading for hierarchical configuration, and background loading for non-critical settings.

## Troubleshooting Configuration Issues

### Common Configuration Problems

Configuration troubleshooting requires understanding common failure patterns and implementing diagnostic capabilities that help identify problems quickly. Typical configuration issues include missing sections, type conversion errors, validation failures, and precedence conflicts.

Missing configuration sections often result from deployment issues, environment differences, or configuration file synchronization problems. Implementing comprehensive validation and clear error messages helps identify these issues during application startup rather than during runtime.

Type conversion errors occur when configuration values cannot be converted to expected types, often due to formatting differences between environments or manual configuration edits. Robust configuration classes include appropriate type handling and conversion logic to minimize these issues.

Configuration precedence conflicts arise when multiple configuration sources unexpectedly provide conflicting values. Understanding the configuration hierarchy and implementing diagnostic logging helps identify and resolve these conflicts.

### Diagnostic Tools and Techniques

Effective configuration diagnostics involve implementing logging, monitoring, and debugging capabilities that provide visibility into configuration loading, validation, and usage patterns. Configuration logging should include information about source precedence, validation results, and runtime configuration access.

Built-in ASP.NET Core logging provides configuration-related log entries, but custom diagnostic logging can provide application-specific insights into configuration behavior. Implementing structured logging for configuration events enables effective monitoring and troubleshooting in production environments.

Configuration debugging tools include techniques for inspecting configuration values at runtime, validating configuration precedence, and testing configuration changes. Development tools can provide configuration visualization, validation testing, and impact analysis for configuration modifications.

```cs
// Example configuration diagnostics
public void LogConfigurationDiagnostics(IConfiguration configuration)
{
    _logger.LogInformation("Configuration sources: {Sources}", 
        string.Join(", ", ((IConfigurationRoot)configuration).Providers
            .Select(p => p.GetType().Name)));
    var weatherSection = configuration.GetSection("WeatherApi");
    _logger.LogInformation("WeatherApi configuration loaded from: {Source}",
        weatherSection.GetDebugView());
}
```
